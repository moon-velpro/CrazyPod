# CrazyPod · 原生 iPod 手感与性能验收基线

状态：目标指标，**不是**当前实机测量结果。适用于 iPod Classic 6/6.5/7G（320×240），ARM SoC + Click Wheel。

## 设计优先级

1. **第一帧反馈优先于复杂动画。** 转盘跨过一个实体档位时，选中态先变；封面、渐变、投影不得阻塞输入。界面克制、排版准确、状态稳定。
2. **音频高于 UI。** Rockbox 解码/PCM、耳机输出、USB、磁盘以及锁屏/电源处理优先。重绘不允许干扰音频线程。
3. **节奏一致而不追虚高 FPS。** 当前帧时钟固定 50fps / 20ms，因为固件 HZ=100 适合精确 2-tick 步进；LCD 能力及 TE/FMARK 同步是硬限制，不追求手机式 120Hz。
4. **一档、一格、一次动作。** 转盘加速仅改变有意义的选项位移；Select 长按/重复不应多次打开应用；退回按钮不能误触重入。
5. **不在转盘的热路径做磁盘 I/O。** 图书、相册、MiniApp/主题加载均退出产品 UI。封面必须优先用缓存和低优先级任务，不在频繁滚动中同步解码。
6. **停止触控即停止无关刷新。** Hold/LCD off 后应等待真正事件，音乐状态持久化和必要唤醒保留，不能人为强制 1Hz 高耗电轮询。

## 需要通过真机建立的目标（暂未测量）

| 指标 | 验收目标 | 当前已具备的观测点 |
|---|---|---|
| Click Wheel 档位到选中态可见 | P95 不高于 50ms | `crazypod_present_get_diagnostics` 中的 Home 渲染/面板提交时间 |
| Home/列表跟手刷新 | 优先保持 50fps（帧周期 20ms），不允许长期积压 | `deadline_misses`、`max_late_ticks`、`home_render_timeouts` |
| 正在播放操作 | 立即完成按键反馈，封面异步呈现，不阻断 PCM | `music_render_timeouts`、`present_timeouts`、音频实测 |
| 进入/返回动效 | 有统一节奏，不闪黑、不撕裂、不能重复激活 | 现有 fixed-point cubic easing + scene transition + full-frame TE 提交 |
| 后台播放和锁屏 | 无可察觉爆音/掉帧，稳定唤醒与恢复 | 长时间真机播放、锁屏/唤醒、USB 插拔测试 |
| 内存与功耗 | 不为 UI 动画引入永久大型缓存或高频空转 | ARM map、堆/栈水位、设备电流 |

20ms 是**软件节奏预算**而非 LCD/SoC 可实现的保证；panel TE 等待可能使单次提交超过预算。必须在设备上统计 P50/P95/最坏情况、卡顿原因、内存峰值，避免只靠模拟器判断流畅。

## 本轮已实现的交互修正

- Home 选中变化仅更新**旧选中行、新选中行**的 LVGL 样式，不再重置全部四行标签或反复执行整个 Home 的布局循环；页面初建和外观刷新仍保持全部行初始化。
- Select 的 `BUTTON_REPEAT` 不再重复启动页面，`BUTTON_REL` 也不会在 Home 被误认为新按键；加入 C99 宿主回归测试。
- 新增 Home 档位触发至实际帧成功提交的微秒级计数：`home_selection_events`、`home_selection_presents`、`home_selection_last_latency_us`、`home_selection_max_latency_us` 和 `home_selection_over_50ms`。同帧连续档位按最早触发计时；LCD 同步失败不计为成功呈现。该计数只能用于实机/模拟器观测，不能当作当前性能已达标的证据。
- 保留 Home 50fps 帧时钟、TE 同步、完整的音乐工作流、播放状态、USB 和存储。没有为了“视觉流畅”不经验证地提高全局 CPU 频率或加大动画内存。

GitHub Actions 的 C99 / 架构 / 严格语言 / ARM 固件 / macOS 模拟器全部最新提交成功；用 320×240 模拟器检查至少 Home、Music、Now Playing、Settings 的字体和切换；使用真机至少验证连续扫轮、快速返回、空音乐库、数千首歌曲库、封面缺失/损坏、长时间音乐播放、USB、Hold/LCD off、唤醒以及冷启动不复位。任何一项未完成，PR 维持 Draft，不将固件标为可安全刷入。

## 2026-11-17 · 转盘画面提交时序修正

发现并修复一处重要的主屏显示竞争条件：原实现会在转盘选中项改变时立刻将整个屏幕排进 LCD 提交队列，而 LVGL 新行样式有可能要等到之后的 50fps 刷新周期才写入 RGB565 帧缓冲。这样可能白白传送上一帧，并让“档位到呈现”统计误把上一帧的成功提交当作响应。

新流程为：转盘档位发生变化 → 立即更新旧/新两行样式并记录单调时间 → 等待 LVGL 最后一次 flush 完成帧缓冲写入 → 才允许将该选中态作为同步全帧提交到 LCD → 同步成功后采样延迟。如果 TE 提交失败，继续重试而不把失败算成已呈现。若用户切换到其他页面或由全屏转场接管，取消尚未完成的主屏统计。

C99 帧时钟宿主测试覆盖：历史整帧不可抢先呈现、连续档位合并按最早时间计时、提交失败后重试、超过 50ms 计数、转场主动取消。主页滚动热路径还把始终不变的玻璃底色、边框宽度与边框颜色留在初始化/外观更新阶段，避免每个档位重新设置这些属性。

**注意：** 这个变更是防错与减少冗余提交，不代表已经得到真机 P95 时延。当前仍使用稳健的 TE 同步整帧路径；是否进一步转向局部行更新，必须在硬件面板撕裂与像素一致性验证后决定。
